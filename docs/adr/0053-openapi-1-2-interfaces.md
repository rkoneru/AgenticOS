# 0053. OpenAPI 1.2.0: identity, approval by id, policy activation, registry and marketplace (additive)

Status: Accepted · Date: 2026-10-02 · Related: 0007 (freeze), 0024, 0025, 0030, 0031, 0042, 0050, 0051

## Context

The Phase 7 exit requires every core workflow to work from the console, the CLI and both SDKs against the real stack. Four gaps were
recorded while the components were built against mocks (NEEDS #231, #236-#238, #243, #244, #252): no identity endpoint (`whoami` could
not show tenant or role, the console invented `/auth/me`), no approval-by-id, no policy activation in `/v1` (the CLI and console used the
admin API), and no registry or marketplace operations in the public API (the CLI and console invented them).

## Decision

One additive bump, `info.version` 1.1.0 -> 1.2.0, per the 0007 procedure (no existing path, parameter, schema, status code or enum value
changes; `FREEZE.json` regenerated; SDKs regenerated by `make sdk-generate`):

- `GET /v1/me` (`getMe`): `{tenant{id,name,region}, member{id,email,display_name,role}, credential{kind,scopes}}`. Any valid credential;
  no scope is needed, so a narrow API key can identify itself. Never reads anything from the request.
- `GET /v1/approvals/{approvalId}` (`getApproval`): same visibility as the list (the requester, or a principal whose role is eligible);
  anything else, including another tenant's id, is 404.
- `POST /v1/policies/{versionId}/activate` (`activatePolicyPack`); `PolicyPack` gains optional `version_id` and `active`.
  Activation runs through the admin API's own guarded path (authorization, audit, kernel bundle publication).
- Registry (tag `Registry`), over `@axis/registry`, tenant and role from the credential: `listRegistryNamespaces`, `claimRegistryNamespace`,
  `listRegistryKeys`, `addRegistryKey`, `publishRegistryBlueprint` (client-signed: detached Ed25519 signature + DSSE provenance, verified
  before storing), `listRegistryVersions`, `yankRegistryVersion`, `resolveRegistryBlueprint` (re-verifies hash, signature and provenance
  on every read; a failure is 422 `validation_failed` whose `errors[].keyword` are the failed check codes, and never falls back to an
  older version).
- Marketplace (tag `Marketplace`), tenant side only: `listMarketplaceListings`, `getMarketplaceListing`, `previewMarketplaceInstall`
  (permission diff against the tenant baseline and the `consent_digest`), `installMarketplaceListing` (pinned to version and content
  hash; the digest must match a fresh evaluation, else 409), `listMarketplaceInstalls`, `uninstallMarketplaceListing`.
  Publisher onboarding, reviewer and moderator actions are NOT in the public API (staff and publisher-console concerns).
- New authorization actions in the control-plane pack: `api.policies.activate`, `api.registry.read|write`, `api.marketplace.read|install`
  (API-key scopes `policies:write`, `registry:read|write`, `marketplace:read|write`). `getMe` is authentication-only (route action
  `null`); everything else is decided by the pack as before.

No new problem `code` values: verification and consent failures reuse `validation_failed` (422) and `conflict` (409) with `errors[]`/`detail`.

## Consequences

- The gateway route table, the SDK generator output, the CLI and the console are regenerated/extended in the same change; the drift tests
  in each stay green.
- Registry publishing needs publisher tooling that runs the ABL compiler (the provenance carries the lint results the verifier
  recomputes). The CLI (`axis registry sign`) and the TS e2e do that; the Python SDK transports already-signed bundles.
- Marketplace publisher and staff workflows remain outside the API (the e2e harness drives them through the services, documented).
